# 主网首发等待时间目标

这些是待实测验证的工程目标，不是已经达到的 SLA。合约候选先定稿；后端性能、ASP 发布节奏与前端测量后续单独上线。

Privacy Cash 官方 EVM SDK 的 [deposit.ts](https://github.com/Privacy-Cash/privacy-cash-sdk-evm/blob/main/src/deposit.ts) 和 [withdraw.ts](https://github.com/Privacy-Cash/privacy-cash-sdk-evm/blob/main/src/withdraw.ts) 包含每 3 秒的索引确认轮询。轮询间隔不是端到端耗时。公开客户端流程未出现本协议逐 note 等待下一次 ASP root 发布的独立阶段；这不能证明服务端完全没有风控。当前未找到官方公布的 Robinhood 证明时间或端到端 P50／P95。桥接文档中的报价等待和新鲜度也不是到账时限。

| 用户操作／阶段 | 初始工程目标 |
| --- | --- |
| 已批准余额：桌面热启动转账／提现 | 端到端 P50 ≤20 秒，P95 ≤45 秒；不额外等下一次 ASP 发布 |
| 桌面本地证明 | P50 ≤10 秒，P95 ≤20 秒；首次下载与手机单列 |
| 新 note 到可花费 | ASP 使用 15 秒档，索引／发布变化检查 1–3 秒；目标 P95 ≤30 秒 |
| 状态与任务接口 | 热读取 P95 ≤1 秒；提交快速返回 job ID，再查询确认状态 |

当前生产配置的发布间隔仍为 60 秒。在持续发布且到达时间均匀的简化模型中，单独这一段平均等待约 30 秒；15 秒档约为 7.5 秒，之后还需加上索引、上链与集合镜像同步时间。16 epoch 窗口支持发布期间继续使用有效证明，不能加快证明本身。是否提前触发、怎样批量发布及 journal 归档属于后端后续工作，本次合约定稿没有修改线上发布频率。

实测按点击、参数就绪、状态就绪、证明完成、ASP 可花费、job 创建、广播、链确认、收款索引分别打点；同链、同设备、同样的冷／热缓存条件比较。记录 P50／P95、失败率、过期后重新证明次数，并区分原生／ERC20／DEX；样本不足时不发布速度承诺。首次初始化的参数验证和下载必须单列，不能藏进正常提现时间。

缩短发布间隔前，先完成增量 receipt 校验、发布 journal 归档与持续确认；保留单写 signer、累计 gas 预算、重组重验和过期状态禁止新花费的门禁。付费 RPC／备用 RPC、事件触发发布和证明预热按测量结果再安排。合约的 16 epoch、1 小时 grace 和 Safe 紧急撤销机制保持本候选定义。
